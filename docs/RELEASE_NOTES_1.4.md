# v1.4.0-rc1 发布说明

日期：2026-11-06。安装和常用行为见 [README](../README.md)，验证结果见 [VALIDATION.md](../VALIDATION.md)。

## 本版解决的问题

旧调用链中，启动探测可能反复创建 broker；连接失败时，PyAEDT 还可能回退为新建桌面。请求超时后立即重试，也可能使原操作与重试重叠。本版将启动等待改为被动探测和单次握手，为已存在的本机目标增加 attach 保护，并保留超时请求以便先核对结果。

这些变化已经过离线控制流程测试，并完成一次独立空白桌面的无界面启动、gRPC 连接、空工程查询和正常关闭。首次烟测发现 socket 枚举的归属假阴性，改为针对已知自启动 PID 握手后复测通过。**求解、建模及长跑的完整实机回归尚未完成**，不能声称所有环境的进程风暴已经彻底解决。本版也不解释或修复不同 AEDT 版本之间的电磁结果差异。

## 兼容性

验证环境为 Windows、Python 3.14.10、PyAEDT 1.9.0、MCP SDK 1.30.0。attach 保护使用 PyAEDT 内部接口，仅对 1.9.0 开启；其他版本及内部接口布局变化会被拒绝。远程 RPC、LSF 和可能覆盖显式目标的环境配置不属于该本机 attach 流程。

安装基线由 `manifest.json` 的 hash 列表决定。只有已列入的源文件与依赖文件组合才允许安装；未知新版上游、缺失的必需文件、本地修改不能靠 `--force` 绕过。当前发布准备没有替换正在使用的服务。

## 调用方需要调整的地方

### 超时与 recovered

超时只说明等待预算已用完。原请求可能仍在 AEDT 内执行，broker 会继续保留它。后续调用先检查这条原请求：尚未返回时报告 pending；已经返回时通过 recovered 提示交回旧响应。**这两种返回都没有执行新命令。**

客户端应展示原请求身份及旧响应，核对副作用，然后再发起下一条明确命令。不要把 recovered 当作重试成功。broker 已退出、服务被重启或结果不可确认时，需要查看日志与工程状态，不能假定写入失败。

同一服务内的 pending 保护不构成跨服务、跨机器或崩溃后的请求去重系统。

### 连接和启动

只给出一个已核实的本机 PID 或端口。端口所有权不明确时先查会话，可改用明确 PID。没有通用的固定端口要求。

一次 launcher 启动失败后，存活的进程保留以便检查；同一 launcher 不会继续叠加该未结束启动。服务重启后不会自动识别所有历史失败启动，使用者仍应先检查现存会话。任意内联 Python 或独立脚本不受默认 Desktop factory 的全部保护。

### 工程路径与创建

`aedt_project_guard.open_project(App, absolute_existing_path, **connection_kwargs)` 用于已有工程；`create_project(App, absolute_new_path, **connection_kwargs)` 用于有意新建。先安装 guard，再导入应用类；已经导入的类不会自动追溯替换。

工程路径默认必须存在；裸名只允许唯一匹配。显式创建拒绝已有工程、锁和结果目录。存在检查与后续构造之间仍有竞争窗口，应使用独立目录和单一写入者。

`None`、空值维持 PyAEDT 活动工程行为，不证明选择了预期项目。guard 不拦截以后所有保存，也不保护其他未加载 guard 的脚本。

### 求解设置与结果

- 交互提交默认不先保存；部分环境中保存可能改变求解器设置。
- 可读的 HFSS 原生 Solver Type/Frequency 在显式保存后改变或变为不可读时，不提交求解；保存本身已经发生，报错不代表工程未被保存。
- 原生读回不支持时返回未确认和警示，不用缓存冒充原生属性；该 HFSS 逻辑不套用到其他求解器。
- batch 调用可能在事前快照后内部保存，因此快照不能证明最终求解器设置。
- `analyze_all.completed` 不再跟随 API 布尔值；改为读取 `api_returned_success`，并检查各 setup 的实际求解记录。
- `running` 是桌面活动状态；空闲不证明指定 setup 的最新求解成功。
- 导出的摘要只描述该文件。即使它写有 Normal Completion 和收敛，仍须核对是否来自当前目标工程、实际频率与本次提交。

收敛解析器仅识别英文原生单频 `Max Mag. Delta S` 表，核查原生结论、完整 pass 序列和连续达标次数。未知格式保持 inconclusive。它没有承诺扫频插值、场分布、远场积分或跨版本物理一致性。

## 安装与恢复的边界

安装前检查整个 payload、目标基线、必需支撑文件及计划中的配置修改；包内 hash 按原始字节严格匹配，目标文本仅容忍已知内容的 CRLF/LF 差异。

每次写入使用唯一批次备份和 journal，目标逐文件原子替换。捕获写入异常时尝试恢复本批次已写文件，只有目标仍等于本次写入内容时才恢复，避免覆盖其他进程的新修改。冲突或恢复失败记录在 journal。

这不是断电、进程终止、磁盘失效下的多文件原子事务。备份写入错误、journal 写入错误或安装后测试失败时，均需要检查实际文件状态；不能只凭安装退出码推断已恢复原状。`--force`、`--revert` 禁用，恢复应围绕明确的单批次备份审查。
